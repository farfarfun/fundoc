# 如何构建"AI 能用"的知识库

> 目标读者：既要给人看，也要给 AI(RAG / Agent)用的知识库维护者。
> 核心判断：AI 知识库的瓶颈从来不是模型和工具,而是内容本身的**结构化程度**和**持续维护机制**。模型越大不代表效果越好——70B 大模型配粗糙的知识库照样幻觉,7B 小模型配干净的 RAG 反而更稳。结构化程度越高(分类体系→本体论→知识图谱),AI 能做的推理就越深、越可解释。

## 1. "给人看"和"给 AI 用"是两种文档

传统文档(Wiki、群公告、口口相传)默认读者是人:人能脑补上下文、能问同事、能容忍格式混乱。AI 检索到的是**脱离上下文的一个片段**,没有机会追问,所以:

- 文档必须自解释(self-contained),不能依赖"看前面那条消息""问一下张三"
- 结构必须显式(explicit),不能依赖标题的心领神会或者截图里的文字
- 每个片段必须能独立成立,又要能追溯回全文

一句话:**写给 AI 的知识库,本质是把"隐性知识"转成"结构化显性知识"。**

## 2. 内容组织:先分类,再分片

### 2.1 原子化:一文一事

- 每篇文档只讲一个主题/一个问题,不要把 FAQ、规则、案例混在一个大文件里
- 文件名/标题即摘要,让人和检索系统都能"看标题猜内容"
- 避免"大而全"的百科式长文——长文对人友好,对分片检索不友好

### 2.2 目录按主题组织,不按组织架构组织

- 目录结构应该反映"问题域",而不是"谁负责的"(部门/项目会变,问题域相对稳定)
- 建议结构:
  ```
  docs/
    concepts/      # 概念、术语、原则
    howto/         # 操作指南、SOP
    faq/           # 常见问题
    decisions/     # 决策记录(ADR),记录"为什么这么做"
    reference/     # 配置项、API、字段表等查阅型内容
  ```

### 2.3 单一事实来源(Single Source of Truth)

- 同一个知识点只在一处维护,其他地方用链接引用,不要复制粘贴
- 复制出来的内容会腐烂(原文更新了,副本没更新),AI 会检索到过时的副本却无法分辨新旧

## 3. 结构化知识的三层工具:Taxonomy、Ontology、Knowledge Graph

上面第 2 节讲的是"文档"这个粒度的组织方式。但当知识库里的核心资产不是"一篇篇文档",而是"实体和它们之间的关系"(比如产品、供应商、订单、组织架构、依赖关系)时,需要更进一步的结构化工具。三者不是互相替代的选项,而是**从骨架到血肉**的三个层次:

| 工具 | 解决的问题 | 能表达什么 | 不能表达什么 |
|---|---|---|---|
| **分类体系(Taxonomy)** | 层级归类 | "苹果 属于 水果 属于 食品"(父子层级) | 实体之间的动词关系,如"人 下单 订单" |
| **本体论(Ontology)** | 语义与逻辑规则 | "Person -placed-> Order -contains-> Product"(带语义的逻辑命题),支持推理(A是B的父类、B是C的父类 ⟹ A是C的祖先类) | 落地存储和查询——本体论是"规则",不是"数据" |
| **知识图谱(Knowledge Graph)** | 落地实现层 | 节点(实体)+ 关系 + 属性 + 组织原则(taxonomy/ontology),用属性图模型存下具体的实例数据,可查询、可推理 | 无(是前两者的落地容器) |

### 3.1 分类体系(Taxonomy):层级骨架

- 树状父子结构,回答"这个东西属于哪一类"
- 技术上常用 SKOS 标准(`broader`/`narrower` 关系),或在图数据库里用 `SUBCATEGORY_OF`/`PARENT_OF` 关系建模
- 适合:统一打标签、分面搜索、维护受控词汇表(避免同义词各写各的,比如"手机号"/"电话"/"联系方式"并存)
- 局限:只能表达"属于"关系,表达不了"A 对 B 做了什么"

### 3.2 本体论(Ontology):语义与推理规则

- 用"主语-谓语-宾语"式的逻辑命题定义实体间的语义关系,例如 `Person -placed-> Order`、`Order -contains-> Product`
- 适合:给人和 AI 一份可共同理解的领域定义;支持逻辑推理("A是B的父类、B是C的父类" ⟹ 推出"A是C的祖先");跨系统对接时用行业标准本体(金融 FIBO、医疗 SNOMED CT、通用 Schema.org)
- 传统实现方式是 RDF 三元组,但三元组把每条关系拆成独立的一行,数据量稍大就会变得冗余、难查询、难维护——这也是后来属性图模型(即知识图谱)流行起来的原因

### 3.3 知识图谱(Knowledge Graph):落地实现层

知识图谱 = 实例数据(节点/关系/属性) + 分类体系和/或本体论作为组织原则。四个组成部分:

- **节点(Nodes)**:实体,如 Person、Order、Product
- **关系(Relationships)**:如 `PLACED`、`CONTAINS`、`TYPE_OF`
- **属性(Properties)**:节点或关系上的键值对,如 `price`、`weight`、`status`
- **组织原则**:taxonomy 和/或 ontology,决定这些节点和关系该怎么摆放、怎么解释

相比"分类体系"和"RDF 三元组",属性图模型的工程优势很直接:

- 同一对节点之间可以有多种关系、同类型关系可以有多个实例,不受预定义结构束缚
- **一条查询语句就能跨层检索**——分类体系、本体论、实例数据可以在一条 Cypher/图查询里一起查出来,不需要应用层拼接多次查询结果

### 3.4 三者怎么协同落地

不是"选哪个",而是"分别负责什么":

1. 明确用例——知识图谱要回答哪些业务问题,这是设计的起点,不要为了建图而建图
2. 设计 Schema:数据有层级/分类需求 → 用 taxonomy 建模;数据需要语义规则/推理/跨系统互通 → 用 ontology 建模
3. 把实例数据按 Schema 灌入知识图谱
4. 随业务演进持续迭代 Schema——不追求一开始就完美,大多数图谱是从简单结构起步,需要正式语义或互操作时才引入本体论

## 4. 文档格式规范

- 统一用 Markdown,标题层级清晰(`#`/`##`/`###`),不要跳级
- 每篇文档头部加 Frontmatter 元数据:

  ```yaml
  ---
  title: 服务重启流程
  summary: 一句话说明这篇文档解决什么问题
  tags: [ops, restart, prod]
  status: reviewed   # draft | reviewed | deprecated
  updated: 2026-09-10
  owner: someone
  ---
  ```

- 关键信息不要只放在图片里(截图里的文字 AI 读不到),配文字说明或表格
- 代码块、命令、配置项用 fenced code block,不要用纯文本描述
- 时效性强的内容(价格、版本号、负责人)要标注更新时间,过期内容要显式标记 `deprecated`,而不是留着不管——AI 分不清"旧的但还能用"和"旧的已经不对了"

## 5. 面向检索的分块(Chunking)策略

给 RAG 用的知识库,最终会被切成 chunk 存入向量库,分块方式直接决定召回质量:

1. **按语义边界切,不按固定字数切**——优先在标题、段落、列表项边界切分,避免把一句话切断
2. **每个 chunk 携带"标题路径"上下文**,例如 chunk 内容前拼接 `服务运维 > 重启流程 > 灰度重启步骤`,这样即使脱离原文也知道自己在讲什么
3. **表格/代码块整体保留**,不要被切成两半,必要时单独作为一个 chunk
4. **chunk 之间保留少量重叠(overlap)**,避免关键信息刚好落在切分边界上
5. **长文档先做摘要 chunk**,配合正文 chunk 一起入库,应对"总览类"提问

## 6. 检索策略:向量检索 vs 图检索(GraphRAG)

- 混合检索优于单一向量检索:向量检索(语义)+ 关键词检索(BM25,精确匹配型号/报错码/专有名词)+ Rerank,三者叠加比单纯堆大 embedding 模型更有效
- **纯向量检索的天然缺陷**:召回的是孤立的文本片段,片段之间的上下文是断裂的,AI 只能"看到什么答什么",答不出需要串联多个事实的问题,也难以解释"为什么这么答"
- **GraphRAG(图检索增强生成)**:当知识库里的关键信息本质是实体关系(依赖链、审批链、组织架构、供应链)时,把这部分知识建成知识图谱(第 3 节),让 Agent 沿关系边做**多跳遍历**,而不是只靠语义相似度匹配文本。例如"某产品供应中断会影响哪些业务",可以从产品出发,沿关系链走到类别→供应商→订单→工单→文档,而不是只检索包含该产品名的文本片段
- 实践建议:**文档类知识**(SOP、FAQ、说明文档)用第 2/5 节的文档级 RAG 就够了;**关系密集型知识**(依赖关系、审批链、实体归属)才值得投入建知识图谱——不要为了追新技术,把简单问题复杂化

## 7. 内容治理:比工具更重要的是维护闭环

工具和模型只是手段,真正决定知识库好坏的是能不能持续沉淀和纠错:

- **建立反馈回路**:AI 答错了 → 定位是"没有这个知识"还是"知识写错了/过时了" → 修文档,而不是只在对话里临时纠正
- **定期清洗**:去掉水印、乱码、失效链接、重复内容
- **明确归属**:每篇文档要有 owner,没人认领的文档大概率会烂掉
- **上线前审校**:新增文档先标 `draft`,经过验证再转 `reviewed`,避免把错误信息第一时间喂给 AI

## 8. 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 模型越大越好 | 大模型幻觉不会因为"大"而消失,粗糙知识库照样答错 | 优先投入在知识库质量,模型按场景选够用的即可 |
| 把内部 Wiki 直接拿去做向量化 | Wiki 的结构依赖大量隐性上下文(链接、目录位置、口头共识),脱离上下文后信息残缺 | 先做"清洗-拆分-补充元数据"的整理,再入库 |
| 建完一次就不管了 | 知识库会随业务腐烂,过时信息比没有信息更危险 | 建立更新机制和 owner 责任制 |
| 只追求向量检索精度 | 语义检索对专有名词、代码、编号类查询效果差,且检索不出跨实体的关系链 | 混合检索(向量+关键词)+ 过滤元数据;关系密集型知识引入 GraphRAG |
| 长文一把梭 | 检索命中大长文时,LLM 拿到的上下文冗余、噪音多 | 原子化拆分,长文档做摘要层 |
| 一上来就搭复杂本体论/知识图谱 | 过度设计,维护成本远超收益,大部分场景根本用不到推理能力 | 先从简单结构起步,业务真的需要语义推理/多跳查询时再引入 ontology/KG |

## 9. 落地检查清单

- [ ] 每篇文档能否脱离上下文独立理解?
- [ ] 是否只讲一个主题?
- [ ] 是否有 frontmatter(title/summary/tags/status/updated/owner)?
- [ ] 关键信息是否都以文字/表格形式存在(而非只在图片里)?
- [ ] 过时内容是否显式标记 deprecated,而不是放任不管?
- [ ] 是否存在多处复制粘贴的重复知识点?
- [ ] 分块时标题路径是否会随 chunk 一起保留?
- [ ] 是否有人负责这篇文档的准确性?
- [ ] 知识库里是否存在"关系密集型"内容(依赖链、审批链、供应链)?如果有,是否评估过用知识图谱/GraphRAG 而不是纯文档 RAG?
